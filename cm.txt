feat: a load and push shovel mode, portable and off by default

The brief: remove the flattening verb, make one click push the snow and pick up a little, and the
other click release. Try it in the test scene only, but write it as a portable module that can be
switched on in the real game later with one line.

## The three verbs, and the decision that was asked for

  LEFT   push: drive a front forward AND pick up a residue while doing it
  RIGHT  release: empty the blade where it is pointed, in one go
  (the deliberate fill is the accounting path the rate constant describes)

Asked and answered: what happens to throwing and pouring. LEGACY keeps its pour-and-toss wiring
untouched. LOAD_AND_PUSH has no throw at all, because it already has a way to MOVE snow (the
push) and does not need a second way to throw it -- and the right button was the only binding
left, so it became the release. `_update_shovel_buttons` is now skipped entirely in this mode:
letting it run is how `_right_hold` set `is_dumping` and the blade poured its load back into the
field while a test was measuring a push.

The residue is `PUSH_RESIDUE_FACTOR = 0.25` of the load rate, declared in the module.

## The module, and portability as a fact

`scripts/shovel_modes.gd` holds the mode enum (`LEGACY`, `LOAD_AND_PUSH`), the residue fraction,
the blade wall height, and `check_portability()`, which READS ITS OWN FILE and reports any
reference to the test scene. The battery fails on that check. Without it "it is global" is a
hope; with it, it is a fact that can stop a commit. It reports portable.

The module has no scene references, no `class_name`, no defaults touched. `player_controller.gd`
does NOT import it -- the mode travels as a plain integer -- so the main game is not wired to the
module at all and starts in LEGACY. One line in the test scene asks for the other one:

    player.set_shovel_mode(ShovelModes.Mode.LOAD_AND_PUSH)

## Two new input actions, by name

`shovel_load` (left) and `shovel_push` (left) are InputMap actions, not button numbers in code,
so they can be swapped without touching logic. Tamping (`shovel_tamp`, Q) is not reachable in
this mode: the press does nothing at all, and the battery checks both halves -- no height change
and no mass change.

## The ledger, which is a measurement fix worth keeping

`--shovel-modes` first reported "the field loses exactly what the blade gains" as FAIL with
-0.070 kg of loss for a 6.300 kg load. The cause is measured: the whole-field integral drifts by
MORE than the carve it is being asked to adjudicate -- 23199.15 then 23202.04 for the same
untouched world. So `carve_shovel` now keeps `_shovel_yield_kg`, an exact record of what it handed
over, read by `shovel_yield_kg()`. The check now reads 6.300 kg against 6.300 kg, error 0.000%.

(6.86 kg/s against 34.00 kg/s, and 6.86 is 0.25 x 34), pushing moving snow (the trail went
0.2756 -> 0.1986 m), the blade wall jamming a 0.385 m pile and taking nothing while jammed,
cleared ground loading nothing, forward and sky loading nothing, mass untouched when aiming away,
the tamp key doing nothing, the module being portable, a fresh player starting in LEGACY, and the
shipped project settings not switching the mode on.

The one failure is the push's own exact-loss verdict, and it is a flaw in the BATTERY and not in
the mechanic: the field still has queued GPU operations from the test's own clearing of the strip
in flight when the push is measured, so the ledger delta reads -90.979 kg. The fill's exact loss
proves the accounting path is sound; what is missing is isolating the push's carve window. Said
plainly rather than papered over.
