## The unconnected signal is now documented rather than left as a trap

`contents_changed` is declared and emitted in THREE container classes (snow_bucket, wheelbarrow,
disposal_test_container) and connected by NOTHING. It is not broken: the HUD reads its container
readout by POLLING `contents_kg` every frame. But a signal that looks like the update path and is
not one is a DECOY -- the next person to write a container will connect to it, see nothing happen,
and have to work out why.

The declaration in `snow_bucket.gd` now says so: that nothing connects, that the HUD polls instead,
that the signal is kept because the parked container work emits it, and that it is the hook to use
if the HUD is ever changed to listen. Deleting it would have been the wrong call while that work
waits.

## `load()` inside functions: measured, and smaller than the count suggests

Six files call `load()` from inside a function (main.gd 10 sites, sound_effects.gd 11,
playground.gd 6, player_controller.gd 3, snow_field.gd 2, world_assembly.gd 1). Reading them rather
than counting them changes the picture:

  * `sound_effects.gd`'s eleven are almost all inside `_init_arrays`, which runs ONCE and fills
    static arrays. One-time disk reads at startup, which is what preloading is. The two that CAN
    repeat are in `get_sound` for the blower loop and the wind loop, and those benefit from the
    resource cache after the first call.
  * `main.gd`'s ten are in `_build_cozy_environment` and `_plant_pine_forest`: level-decoration
    assets read on the level-start frame. Real, and worth moving to `preload`, but decoration.
  * `world_assembly.gd`'s one is deliberate and documented: the props script path is an ARGUMENT so
    the module does not need to know the project's file layout.

So the honest reading is that this is tidiness and one modest hot-path improvement, not a defect.
Recorded as such rather than as a headline, because inflating it would make the next audit's numbers
less useful.

## The last red, with its cause now measured rather than assumed

`--shovel-modes` 16 OK / 1 FAIL: the push's own ledger verdict. The mechanic is correct and measured
(pushing feeds 8.50 kg/s against a declared 8.50; the blade takes 17.000 kg in 2.00 s).

The verdict reads 173.471 kg of "field loss" against that 17.000 kg blade. That is NOT mass leaving
the world: it is the battery's own setup. `snow_field` now keeps TWO ledgers, and the reason is this
battery:

  * `shovel_yield_kg` counts only `carve_shovel`, which is the right ledger for a blade.
  * `carve_yield_kg` counts every route out, including the radial `carve` this battery's setup uses
    to clear its strip.

With only the blade ledger the setup's kilograms were never in the number being subtracted, and no
reset can remove what was never counted -- which is why the verdict was stuck at -90.979 kg before
and reads 173.471 kg now: the all-routes ledger SEES the queued clearing that the blade ledger was
blind to. The instrument got more honest and the discrepancy got bigger, which is the honest
direction for a measurement problem to move.

What remains is a measurement window, not a mechanic: the setup's clears are queued GPU operations
that land inside the push window no matter when the reset is taken, so the push needs its own
delta taken from a ledger that only the push feeds. That is the next step, and it is written down
with the number rather than guessed at.
