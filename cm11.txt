fix: the machine pays per kilogram, not per fragment

The economy imbalance that the throw fix exposed, and it was real money: `ceil` was applied PER
EMISSION and the machine emits once per body it swallows, so every fragment of a shattered ball was
worth a whole coin.

## Measured

A thrown ball broke on arrival into eight pieces. The machine took 0.546 kg and paid **8 coins**,
where the declared `ceil(kg * 2.5)` says **2**. Four times the rate -- and the more a ball shattered,
the more it was worth, which is exactly backwards: breaking snow should not be a way to print money.

## The fix, and why this shape

The payout is computed on the RUNNING TOTAL: `coins = ceil(total_kg * rate) - already_paid`. Both
scenes keep two accumulators for it (`_sent_kg`, `_paid_coins`).

  * The declared rate is unchanged. A price per kilogram still means a price per kilogram.
  * The per-delivery floor is gone, which is the whole defect: `ceil` treats every delivery as worth
    at least one coin, which is right for a bucket and wrong for a crumb.
  * Rounding once on the total rather than once per delivery is also marginally CHEAPER to the
    player's benefit of the doubt: 3.70 kg then 5.394 kg pays 10 then 13 (23 in all), where rounding
    each delivery separately pays 14 and overpays by one. Measured, both in the game and in the
    battery.
  * It is deterministic and checkable: the coins paid are always exactly `ceil(total * rate)`.

## The batteries had to be taught the same arithmetic

`--disposal-machine` asserted `ceil(kg * rate)` per delivery and went red the moment the game stopped
doing that (22 OK / 0 FAIL -> 20 OK / 2 FAIL). It now keeps its own copy of the ledger and computes
`_owed_for(kg)` as the same difference the game computes, with the reason written where the helper
is. --disposal-machine is back to **22 OK / 0 FAIL** and --tool-ownership reaches **37 OK / 0 FAIL**.

## And one defect that was mine, caught by the gate

`--tool-ownership` reported "4 script errors in the log" while passing in isolation. The cause was
its own state 6: it built a "fresh player" with `player.get_script().new()`, which has no `Camera3D`
child, so the node's `_ready` failed on `$Camera3D/HandRoot` and printed a SCRIPT ERROR four times.
**A node built from a script alone is not a player; the scene makes the player.** The grant contract
is now exercised on the player that exists: state 1 already recreates the save slot, so it starts
with hands only, and the transition to all four tools is the thing being checked. Same two checks,
no invalid node, no errors in the log.

Worth stating plainly: this one was invisible to a battery run by hand and only the gate's
script-error count found it. That count is doing real work.
